# Методическое руководство: параметры запроса

## Результат занятия

За 90 минут учащийся создаёт и объясняет endpoint `GET /hello`, который принимает обязательные `location` и `name`, а затем возвращает точную строку приветствия. Перед просмотром образца ответы и код следует сделать самостоятельно; модельные ответы приведены после заданий.

## Подготовка преподавателя

До занятия преподаватель проверяет наличие JDK 17, доступность Maven Wrapper и чистый запуск проекта. Нужно подготовить один браузер или терминал с `curl`, открыть `HelloController`, тест контроллера и `pom.xml`. Не следует заранее показывать готовый метод: для входной диагностики понадобится пустой лист или заметка учащегося.

## Входная диагностика

Первые 5 минут этапа 0–10: попросите без подсказки разобрать `/hello?location=moon&name=John`, назвать путь, два имени параметров и предсказать статус при отсутствии `name`. Зафиксируйте ответ, не оценивая код. Модель: путь — `/hello`; `?` начинает query string; `&` разделяет параметры; отсутствие обязательного `name` даёт 400. Если ответ неверный, к модели возвращаются в этапе 0–10.

## Пошаговое создание

1. В Spring Initializr выберите Maven, Java 17 и Spring Web; group — `com.example`, artifact — `request-parameters`.
2. Создайте класс `HelloController` в том же или вложенном пакете относительно основного класса приложения.
3. Объявите `public class HelloController` и пометьте класс `@Controller` и `@ResponseBody`.
4. Создайте публичный метод, помеченный только `@GetMapping("/hello")`: отдельная `@ResponseBody` на методе не нужна.
5. Добавьте аргументы `@RequestParam(name = "location") String location` и `@RequestParam(name = "name") String name`.
6. Верните строго `"Welcome to the " + location + " " + name + "!"`.
7. Запустите приложение и проверьте `http://localhost:8080/hello?location=moon&name=John`.

### Самостоятельная попытка

Сначала напишите сигнатуру метода и предскажите ответы на три запроса: корректный, без `name`, с параметрами в обратном порядке. Не открывайте следующий раздел, пока не сформулируете ответы.

### Модельный ответ

```java
@Controller
@ResponseBody
public class HelloController {
    @GetMapping("/hello")
    public String hello(
        @RequestParam(name = "location") String location,
        @RequestParam(name = "name") String name) {
        return "Welcome to the " + location + " " + name + "!";
    }
}
```

Корректный запрос даёт `200` и приветствие; отсутствие `name` — `400`; обратный порядок даёт тот же успешный результат, так как связывание идёт по имени.

## Намеренное несовпадение (deliberate mismatch)

Измените путь временно на `@GetMapping("/greeting")`, но отправьте старый запрос на `/hello`. Объясните, почему получите `404 Not Found`: ни один метод не сопоставлен с этим путём. Верните `/hello` и убедитесь, что проверка снова успешна.

Второй вариант: временно написать `@RequestParam(name = "place")`. Запрос с `location=moon` вернёт `400`, потому что ожидается обязательный `place`. После наблюдения обязательно восстановите контракт `location`.

## Практика

1. Отправьте значения с пробелами: `New%20York` и `Mary%20Jane`.
2. Отправьте `name` перед `location`.
3. Добавьте `language=English` и объясните, почему ответ не меняется.
4. Удалите по очереди каждый обязательный параметр и зафиксируйте статус.
5. Напишите MockMvc-проверку статуса и точного текста для одного собственного успешного примера.

После самостоятельного выполнения сравните: пробел в URL кодируется; порядок не важен; лишний параметр не читается контроллером; отсутствие `location` или `name` означает `400`.

## Вопросы для защиты

1. Почему строка после `?` не является частью пути?
2. Почему недостающий `@RequestParam` даёт 400, а неверный путь — 404?
3. Зачем фиксировать `name = "location"`?
4. Чем полезен `@ResponseBody` в этом задании?
5. Почему `curl` получает URL в кавычках?

### Модельные ответы для защиты

1. Путь определяет обработчик, а query string передаёт значения обработчику после сопоставления пути.
2. При 404 подходящего маршрута нет; при 400 маршрут найден, но запрос не удовлетворяет требуемым параметрам.
3. Так контракт API явно связывает URL-ключ с Java-аргументом.
4. Он отправляет строку напрямую как HTTP-тело, без HTML-представления.
5. Кавычки защищают `&` от интерпретации оболочкой и сохраняют URL одним аргументом.

## Итоговый чек-лист защиты

- Учащийся показывает корректный URL и читает роль `?`, `&` и URL encoding.

- Называет оба обязательных `@RequestParam` и причину HTTP 400 при пропуске любого из них.
- Демонстрирует точное тело `Welcome to the moon John!` и допускает обратный порядок параметров.
- Показывает один MockMvc-тест с проверкой статуса и тела, а также объясняет `contextLoads()`.
- Формулирует разницу между 404 для неверного пути и 400 для неполного запроса.
